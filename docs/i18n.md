# Adding a new language

agent-agenda's frontend is translated with [Paraglide](https://inlang.com/m/gerre34r/library-inlang-paraglideJs)
(part of the inlang ecosystem). Each language is a single flat JSON file of key/value
pairs. Adding a language means copying the English file, translating the values, and
registering the locale. The only code touch is an optional display name for the
language picker.

## How it works

- **English is the base locale.** It is the source of truth for which keys exist and is
  the fallback when another language is missing a key. It is set in
  `frontend/project.inlang/settings.json` as `"baseLocale": "en"`.
- **One file per language** lives in `frontend/messages/`. The catalog path is configured
  in the same settings file:

  ```json
  "plugin.inlang.messageFormat": {
    "pathPattern": "./messages/{locale}.json"
  }
  ```

  So English is `frontend/messages/en.json`, Italian is `frontend/messages/it.json`, and a
  new locale `xx` would be `frontend/messages/xx.json`.
- **Catalogs are not used directly at runtime.** The Paraglide Vite plugin compiles every
  message into typed functions under `frontend/src/lib/paraglide/` at build/dev time
  (zero-runtime). That output is generated and **gitignored** — never edit or commit it.
  The plugin is wired up in `frontend/vite.config.ts`:

  ```ts
  paraglideVitePlugin({
    project: './project.inlang',
    outdir: './src/lib/paraglide',
    strategy: ['localStorage', 'preferredLanguage', 'baseLocale'],
  })
  ```

- **The language switcher reads the locale list directly.**
  The language `<select>` in the settings page (`frontend/src/routes/settings/+page.svelte`)
  iterates over `locales` (re-exported from `frontend/src/lib/i18n.ts`, which itself comes
  from the generated Paraglide runtime). It renders one option per locale, labelled from the
  page's `LANG_NAMES` map or, as a fallback, the uppercased code (`EN`, `IT`, ...). Because it
  is driven by the list, **a new locale shows up in the switcher automatically** once it is
  registered and the project is rebuilt (add its display name to `LANG_NAMES` for a nicer label).

## The message file format

Each catalog is a flat JSON object. The first key is a schema marker that must stay
exactly as-is:

```json
{
  "$schema": "https://inlang.com/schema/inlang-message-format",
  "app_name": "Agent Agenda",
  "settings_title": "Settings"
}
```

- `$schema` tells inlang/editors this is an inlang message-format file. Keep it; do not
  translate it.
- Every other entry is `"key": "translated string"`. Keys are flat (no nesting) and must
  be **identical across all languages** — the key is the stable identifier the code calls;
  only the value changes per language.

### Parameterized messages

Some messages contain placeholders in single curly braces. They are filled in at runtime,
so you must keep them verbatim — same name, same braces — and only translate the words
around them. Current examples:

```json
"dash_done_aria": "{done} of {total} done today",
"dash_today_count": "{done}/{total} today"
```

The Italian catalog keeps the same placeholders:

```json
"dash_done_aria": "{done} di {total} fatti oggi",
"dash_today_count": "{done}/{total} oggi"
```

If you rename, drop, or translate a placeholder, the message breaks. You may reorder
placeholders to fit the target language's grammar, but the names (`done`, `total`, ...)
must be preserved.

## Steps to add a language

The locale code is a [BCP-47](https://en.wikipedia.org/wiki/IETF_language_tag) tag, e.g.
`fr`, `de`, `es`, or a regional form like `pt-BR`. The examples below use `xx`.

1. **Copy the base catalog.** From the repo root:

   ```bash
   cp frontend/messages/en.json frontend/messages/xx.json
   ```

2. **Translate the values.** Open `frontend/messages/xx.json` and translate every string
   value to the new language. Rules:
   - Keep every **key** unchanged.
   - Keep the `$schema` line unchanged.
   - Keep `{param}` **placeholders** unchanged (see above).
   - Keep the **set of keys in sync with `en.json`** — same keys, no extras, none missing.
     English is the source of truth; if you add a key, add it to `en.json` first.

3. **Register the locale.** Add the code to the `locales` array in
   `frontend/project.inlang/settings.json`:

   ```json
   "baseLocale": "en",
   "locales": ["en", "it", "xx"],
   ```

   Do not change `baseLocale` — English stays the base.

4. **Rebuild so Paraglide regenerates.** From `frontend/`:

   ```bash
   cd frontend
   bun run build
   ```

   The Vite plugin recompiles the catalogs into `src/lib/paraglide/`, picking up both the
   new file and the new locale. During development `bun run dev` regenerates on the fly.

5. **Add a display name (optional).** Add the language to the `LANG_NAMES` map in
   `frontend/src/routes/settings/+page.svelte` (e.g. `xx: 'Xxxxx'`); without it the
   picker shows the uppercased code (`XX`).

6. **Verify.** Run the app (`bun run dev` in `frontend/`, or `docker compose up -d --build`
   from the repo root), open **Settings → Language**, pick the new language, and check
   that the UI, including dashboard counters that use `{done}/{total}`, renders
   correctly.

## Style conventions

- **No emoji in UI strings.** Keep copy plain and functional — match the tone of the
  existing English and Italian catalogs.
- **No hardcoded strings in components.** Every user-facing string goes through a message
  key so it can be translated; never inline literal text in a Svelte component.
- **Stable keys.** Treat keys as an API. Rename them only when you also update every
  catalog and every call site; prefer adding a new key over repurposing an old one.
- **Centralized dates/formatting.** Don't bake locale-specific date or number formatting
  into translated strings. Dates are formatted with the browser's `Intl` APIs for the
  active locale (`frontend/src/lib/format.ts`, `frontend/src/lib/time.ts`).

## What is not translated

- **Task content** (titles, notes, steps, closing messages) is stored as written.
- **Natural-language dates** sent by agents (`when`) are parsed on the server in
  English, plus a few Italian forms (`domani`, `dopodomani`, `stasera`, `tra 2 ore`, …).
  Adding a UI language does not extend the parser.
